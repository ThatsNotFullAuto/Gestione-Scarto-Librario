# Repository Guidelines

## Project Structure & Module Organization

The deployable WordPress plugin lives in `gestione-scarto-librario/`.

- `gestione-scarto-librario.php` contains bootstrap code, migrations, REST endpoints, and WordPress hooks.
- `src/index.tsx` and `src/index.css` contain the React/TypeScript interface and styles.
- `includes/` and `templates/` contain PHP modules and server-rendered views.
- `dist/` is generated by the build and must be committed with frontend changes.
- `security-tests/` contains non-destructive smoke tests and controlled staging tests.
- `docs/` contains current operational material and historical design records.
- `releases/` contains signed-off installable artifacts; never edit ZIP contents manually.

## Build, Test, and Development Commands

Run commands from `gestione-scarto-librario/`:

```bash
npm ci
npm run dev
npm run type-check
npm run check
npm run test:security:smoke:self
npm run release
```

`npm run check` validates PHP parsing, security invariants, TypeScript, dependencies, and production assets. `npm run release` also creates a deterministic WordPress ZIP.

## Coding Style & Naming Conventions

Use four-space indentation and semicolons in TypeScript. Use `PascalCase` for components and interfaces, `camelCase` for TypeScript functions and variables, `SCARTO_*` for constants, and `scarto_` plus `snake_case` for WordPress PHP functions. Keep user-facing text in Italian.

Sanitize inputs, escape outputs, validate REST schemas, check capabilities and nonces, and prepare dynamic SQL with `$wpdb->prepare()`. Preserve the anti-lockout recovery path for every security change. Edit `src/`, not hashed files in `dist/`.

## Testing Guidelines

Run `npm run check` for every change. Test activation, upgrades, REST permissions, catalog import, concurrent reservations, email, PDF, backup/restore, retention, and GDPR workflows on staging when affected. Never use real personal data in fixtures or automated tests.

## Commit & Pull Request Guidelines

Use short imperative commits, for example `fix(api): isolate reservation rate limits`. Pull requests must explain user impact, verification, schema/privacy implications, rollback steps, and screenshots for UI changes. Include regenerated `dist/` files, but exclude `node_modules/`, production exports, credentials, logs, and real catalogs.
